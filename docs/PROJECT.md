# done-coding-schema 立项说明

> 文档定位：规范 · 2026-11-24 立项。本页写目标、范围、验收与边界；做到哪了看 `docs/governance/`。

## 目的

HTTP JSON 接口里前后端都要认的通用结构，在这里只定义一次；各语言的类型与模型由定义生成，发布成包，前端、后端各自引入。使用方不再各自手写一份。

改结构时，没跟上的使用方在类型检查或校验时失败，而不是上线后才发现对不上。

## 范围

**首版放进来的结构：**

- 成功外壳：`{code:"OK", message, data}`；
- 错误体：HTTP 状态表达大类，包体带字符串业务码、说明、能否重试、是否已执行、出错字段定位；
- 三种列表，数据都放 `items`，翻页信息各放各的位置：
  - 一次性列表 `{items}`：只用于条数有固定上限的结果（下拉选项等）；
  - 页码式 `{items, page{totalRecord, pageSize, totalPage}}`：给人翻页的表格；请求参数用 `page.*` 前缀；
  - 游标式 `{items, cursor{next, hasMore}}`：消息流这类接着往下取的列表，不带总数；请求参数用 `cursor.*` 前缀；
- 筛选参数的命名规则：`filter.<字段>.<操作>`，首版只有 `eq`；
- 通用业务码（成功一组、失败一组），以及「一个服务的专有业务码清单」的格式；
- 字段命名（小驼峰）与时间格式（带时区的 RFC 3339）约定。

逐字段的规格见批次条目 `08byqy`，定义文件落地后以 `schemas/` 为准。

**不放进来的：**

- 任何具体业务资源的结构；
- 界面如何展示某个字段（控件、列、筛选项）这类元数据；
- 系统之间的事件、凭据格式；
- 带请求体的搜索接口、程序之间同步数据用的游标、健康检查的包体：首版不做，有真实需求再加。

## 产物

| 产物 | 说明 |
|---|---|
| 定义文件（JSON Schema，一个结构一个文件） | 唯一来源 |
| npm 包 | 由定义生成的 TS 类型与常量，连同定义文件一起导出；能在浏览器端引入 |
| PyPI 包 | 由定义生成的 Pydantic 模型与常量 |

两个包从同一个提交构建，用同一个版本号。本仓与两个包都公开。

## 设计取舍

- **标准是严格的，不带开关。** 包只描述这一套结构，不提供「传入自定义成功码」之类的定制入口。后端不按这套结构的项目不引本包，在自己的请求层里适配。
- **业务码是可扩展的。** 通用码以常量导出；错误体的 `code` 字段类型是开放字符串，各服务可以有自己的专有码。使用方遇到不认识的码，按 HTTP 状态归类处理。
- **三种列表是三个类型，不合成一个。** 页码式能跳页、有总数；游标式只能接着取、没有总数。合成一个只能把字段全写成可选，类型检查与校验都会失效。三者共用 `items`，读数据的代码可以通用。
- **不另出 HTTP 状态码枚举。** 各语言都有现成的；本包只给「通用业务码对应哪个 HTTP 状态」。

## 怎么算完成（首版）

1. 每个结构有一份定义，并各带「合法」「不合法」两组样例；样例经定义校验的结果与预期一致。
2. TS 类型与 Pydantic 模型都由定义生成并入仓；手改任一生成物，一致性检查失败。
3. 同一组样例，Python 模型的接受与拒绝结果和定义校验一致。
4. 两个包能在本机构建出来，版本号一致；有一道检查在两者版本不一致时失败。
5. README 写明怎么引入、怎么用。

发布不在「完成」之内，每次发布由维护者决定。

## 边界

- 不在 master 上直接改，在开发分支上做，经合并请求进入发布分支；不自行 push、不自行发布。
- 改字段、加减结构属于改契约：先写下改什么、为什么、影响谁，由维护者决定。
- 引入依赖时写明许可证；只引入发布满 14 天的版本。
- 本仓是公开仓：文档、提交说明与代码里不写任何不公开的项目名、内部路径或内部决策编号。
