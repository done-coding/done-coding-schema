# PyPI 包：由同一份定义生成 Pydantic 模型

## 为什么

后端也要用这套通用结构。本条让 Python 这边从同一份定义拿模型，保证和 TS 那边是同一个东西，而不是另写一份。

## 交付

1. `python/` 下一个可构建的 Python 包，内容是由定义生成的 Pydantic 模型与业务码常量。
2. 生成命令并入上一批的生成与一致性检查。
3. 用同一组样例的 Python 侧测试。
4. npm 包与 Python 包的版本一致检查。

## 怎么算完成

- 同一组样例：合法的 Python 模型都能解析，不合法的都被拒；结果与定义校验逐条一致。有不一致的（生成工具表达不了某条约束）逐条列出并写明怎么补。
- 手改生成的模型后跑一致性检查，退出码非 0。
- 把两个包的版本号改成不一样后跑版本检查，退出码非 0。
- Python 包能在本机构建出 wheel。

## 自己定与不能动

- 自己定：包内结构、测试写法、生成参数。生成工具先试 datamodel-code-generator（MIT）；不合用时写下比较再换，写明许可证。
- 带点号的参数名（`page.pageSize`、`cursor.limit`、`filter.status.eq`）在 Python 侧用别名表达：模型字段是合法的标识符，别名是线上的参数名。
- 模型输出一律小驼峰；成功外壳与三种列表做成可带元素类型的泛型，便于使用方写 `成功外壳[页码式[某资源]]`。
- **泛型与别名怎么办（已定，不用问）**：生成工具做不出泛型或点号别名时，允许在生成物之上手写一层很薄的包装（只把 `data`、`items` 的元素类型换成类型参数、给带点号的参数加别名，不新增、不改名、不放宽任何字段），放在与生成物分开的文件里；同一组样例要同时跑过生成的模型与包装层，两者的接受与拒绝结果必须一致。
- 不能动：定义本身。发现定义要改才能生成，回上一批的定义处理，并报用户。
- 不发布、不 push。

## 上报条件

- 生成工具对某条约束无法表达，且上面允许的薄包装也补不了；
- 本机连不上 PyPI 导致依赖装不上：直接报，不反复试。
